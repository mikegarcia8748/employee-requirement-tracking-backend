## Findings

### SEC-41 — A rendered email body carrying a live recovery PIN already exists, and PRD §12 says PINs are never emailed  [High]  [A04:2025]  *(outside ERT-300; found via architecture §4)*

**Where:** `src/data/notify/NotificationMessages.kt:42-49`; `src/data/notify/OutboxNotifier.kt:88-97`;
`src/domain/port/Notifier.kt:10-18`

```kotlin
// NotificationMessages
fun recoveryPin(employee: Employee, pin: AccessPin) = RenderedMessage(
    subject = "Your recovery PIN",
    body = """
        Hi ${employee.firstName},

        Your recovery PIN has been generated: ${pin.value}
    """.trimIndent()
)

// OutboxNotifier
override suspend fun sendRecoveryPin(to: EmailAddress, employee: Employee, pin: AccessPin) = queue(
    kind = NotificationKind.RECOVERY_PIN, to = to, employee = employee,
    message = messages.recoveryPin(employee, pin),
)
```

**What.** Four documents state the rule and state it absolutely:

| Source | Wording |
|---|---|
| PRD §12 | Recovery PINs are "stored hashed, never logged, **never sent by email at all**" |
| PRD §5 | "delivered out-of-band … **It is never sent by email** (§6.6)" |
| architecture §12, invariant 4 | "a recovery PIN is **never emailed** and reaches exactly one response, once" |
| `CLAUDE.md` invariant 4 | "A PIN is **never emailed**: only the one-time HR recovery response may carry an `AccessPin`" |

The code holds a method that takes an `EmailAddress` and an `AccessPin`, a rendered body that
interpolates `pin.value` in plaintext, and an outbox kind to queue it under. The one thing standing
between that and a PIN in an inbox is that nothing calls it yet.

**The port's own KDoc states a materially weaker rule than all four**, and that is how it got here:

> **only [sendRecoveryPin] accepts an [AccessPin].** Every other method is structurally incapable of
> carrying the credential, so the rule "**no email other than a recovery notification ever contains
> the PIN**" is enforced by the type system rather than by reviewer vigilance.

"No email *other than a recovery notification*" is not the rule. The rule is "no email". The type
system is indeed enforcing something — it is enforcing the weaker rule, and it makes the forbidden
case the single representable one.

**What is not wrong.** `NotificationKind.RECOVERY_PIN` carries `storesBody = false`, so the body is
never persisted. Invariant 4's *other* half — "no stored artefact holds a live PIN" — holds, and the
`storesBody` mechanism is the thing holding it. This finding is only about transmission.

**Impact.** §12 lists the PIN rules under **P0 controls**, and the reason is SEC-03: the recovery PIN
exists precisely because the invitation email may have gone to the wrong person. Emailing the recovery
credential to the same address returns the system to the state the PIN was introduced to escape. The
§12 residual-risk acceptance for link-only portal access is written on the assumption that the
recovery path is out-of-band.

**Reachability.** **Not reachable today — there is no caller in `src/`.** `ERT-650`
(`POST /api/employees/{id}/recovery-pin`) is the ticket that issues a PIN and is `Not started`;
ERT-640 and ERT-643 are adjacent. The finding is that the machinery is **pre-built and named for the
job**: an engineer writing ERT-650 finds `Notifier.sendRecoveryPin` and `messages.recoveryPin` ready,
with a KDoc telling them a recovery notification containing the PIN is the intended exception.

**Test coverage.** `NotifierContract` asserts both implementations queue and never throw; nothing
asserts a PIN does not reach a message body. No test could fail today, because no test is wrong.

**Recommended fix — a decision, not a patch.** Either the four documents are right and the method must
go (HR reads the PIN from the one-time response, and any notification says only *that* a PIN was
issued, never what it is), or there is a deliberate exception nobody has written down and §12 must be
amended to carry it. **The port KDoc must not be the place that decision lives.**

If the documents stand, the shape that makes it unrepresentable is the one architecture §4 already
claims: **no `Notifier` method accepts an `AccessPin`**, and `recoveryPin` renders a body that names
no credential. **Folded into ERT-650**, which owns recovery-PIN issuance, as a criterion that gates it.

Only ERT-650. ERT-640 *verifies* a PIN and ERT-643 calls `notifyHrOfSuspension`, which carries no
credential — neither touches the send path, and filing against them would be noise on two tickets that
cannot reach the defect.

### SEC-38 — Two of the nine §6.4 settings can never be saved: the credential guard refuses their own key  [High]  [A04:2025]

**Where:** `src/data/mapper/AuditEntryMapper.kt:104`;
`src/data/repository/ExposedAppSettingsRepository.kt:132`; `src/data/mapper/AppSettingMapper.kt:43-45`

```kotlin
// ExposedAppSettingsRepository.auditEntryFor
metadata = changes.flatMap {
    listOf("${it.setting.key}.old" to it.old, "${it.setting.key}.new" to it.new)
}.toMap(),

// AuditEntryMapper.refuseCredentials
val named = CREDENTIAL_KEY_FRAGMENTS.firstOrNull { it in lowered }
require(named == null) { "Audit metadata key '$key' names a credential ('$named')…" }

private val CREDENTIAL_KEY_FRAGMENTS =
    listOf("pin", "token", "password", "passcode", "secret", "otp", "credential")
```

**What.** Two of the nine `LinkPolicySetting` keys are `portal.pin_attempts_before_lockout` and
`portal.pin_failures_before_suspend`. `auditEntryFor` turns each changed key into two metadata keys,
`"<key>.old"` and `"<key>.new"`. `refuseCredentials` lowercases the metadata key and refuses it when
any fragment appears **as a substring** — and `"pin"` is a substring of both. So:

`updateLinkPolicy(policy.copy(pinAttemptsBeforeLockout = 6), actor)` → `validateAgainst` passes →
`apply` writes the row and `check(rows == 1)` succeeds → `insertAuditEntry` → `toMetadataJson` →
`refuseCredentials` → **`IllegalArgumentException` thrown out of `factory.transaction { }`.**

The transaction rolls back, so nothing is corrupted. But the exception escapes a method whose declared
contract is `DomainResult<Unit>`, and the two settings are permanently unsaveable.

**This is the same guard as C25, from the other side.** C25 — open, owned by ERT-450 — is the
**value**-side false positive: a typed duplicate reason with no spaces is credential-shaped and becomes
a user-reachable 500. SEC-38 is the **key**-side false positive: a legitimate setting key contains a
fragment and a feature is permanently broken. C25's disposition was deliberate and correct —
*"weakening a tripwire is a specification change"* — and it pinned today's behaviour with a named test
rather than changing it. That reasoning does not transfer: C25's trap is reachable-but-rare, and
SEC-38's is unconditional on two of nine inputs.

**Impact.** Two of the nine values §6.4 promises are admin-configurable are not, and they are precisely
the PIN lockout thresholds that ERT-642 (temporary lockout) and ERT-643 (auto-suspend) tune. §8.10's
own criterion — *"the session duration and the recovery-PIN lockout and suspend thresholds in §6.6 are
configurable within bounds alongside the expiry values"* — cannot be met. The Phase 2 settings screen
answers 500 on any save touching either.

`AuditEntryMapper`'s KDoc offers "the escape hatch is to rename the key", which is cheap for a use-case
author choosing a metadata key. Here the key is the `app_settings` **primary key**, so renaming it
costs a migration, a `LinkPolicySetting` change, a V3 seed change and a `SeedDataTest` change.

**Reachability.** `updateLinkPolicy` has no caller until the Phase 2 §8.10 screen — latent today, and
guaranteed to fire on the first save that touches either threshold. ERT-310's KDoc insists the method
"is not dead code awaiting removal", which is the right call and is exactly why this matters: it is
written, tested, and wrong on two of nine inputs.

**Test coverage.** None, and the matrix cannot see it. The eleven `updateLinkPolicy` tests in
`ExposedAppSettingsRepositoryTest` change `absoluteExpiryDays`, `sessionMinutes`, `lockoutMinutes` or
`completedGraceDays`; the four contract tests change `absoluteExpiryDays`, `idleExpiryDays`, or
nothing. The two `pin*` fields appear only as fixture defaults in `policyWith`, never as the value
under change. ERT-310's fifth acceptance criterion — *"Given any settings change, then it is written to
the audit log"* — is ticked against a subset that excludes both failing cases. See **HAR-19** for why
the contract suite could not have caught it either.

**Recommended fix:** `refuseCredentials` exempts metadata keys derived from `LinkPolicySetting`, which
is a closed enum rather than caller-chosen text. The denylist stays exactly as strict for every other
caller and **C25 is untouched**. The exemption must be a declared, closed list derived from
`LinkPolicySetting.entries` — not a second regex, which would be a wider hole than the one it patches.

With it goes the guard that makes this class of collision a build failure rather than a Phase 2
surprise: a test over `LinkPolicySetting.entries` asserting every derived metadata key is accepted, so
a tenth setting named `portal.otp_window_minutes` fails the build the day it is added. **Written as a
contract test**, for HAR-19's reason. **Folded into ERT-310, reopened.**

### SEC-39 — `extend_on_rejection_days` can outrun the absolute ceiling, which is §6.4's named failure mode  [Medium]  [A04:2025]

**Where:** `resources/db/migration/V3__app_settings.sql`; `src/data/mapper/AppSettingMapper.kt:227`

```sql
-- Must move the window by at least a day to be worth anything; capped so one rejection cannot
-- outrun the absolute ceiling.
select 'link.extend_on_rejection_days', '30', 'INT', '1', '90'
```

**What.** `link.absolute_expiry_days` is bounded `7..180`; `link.extend_on_rejection_days` is bounded
`1..90`. Both are independently settable. PRD §6.4 is explicit about what the second one does:
*"Pushes the absolute expiry out when HR rejects a document."* So with `absolute_expiry_days = 7` and
`extend_on_rejection_days = 90`, one rejection pushes a live link out to 97 days from issue — **near
13× the ceiling the same file calls hard.** `link.completed_grace_days` (`1..90`) has the same shape
with a weaker consequence.

V3's header names two cross-field invariants, says they "**CANNOT** be expressed in per-row
min_value/max_value", and hands both to ERT-310 by name. ERT-310 implements both, with vacuity guards
on each — `warn exactly one day before expiry - is accepted`, `suspend equal to the lockout threshold -
is accepted`. This third invariant is stated in a comment as an *achieved property* and delegated to a
static bound that cannot express it, so it was never handed to the validator and never implemented.

**Impact.** §6.4's stated fear is that "a well-meant edit cannot turn a token into a permanent
credential", and both `LinkPolicy` and `ExposedAppSettingsRepository` repeat it.
`extend_on_rejection_days` is the one lever that extends a live link, and it is the one lever with no
cross-field rule. `LinkPolicy`'s KDoc says the ceiling kills the link "regardless of activity"; today an
admin can make that false through the settings screen without any value leaving its own range.

**Reachability.** Phase 2's §8.10 screen. Also today from any direct edit to `app_settings` —
`crossFieldErrors()` runs on **read** as well as write, so the rule, once added, would refuse a bad
stored combination at read time and fail loudly rather than issuing over-long links.

**Test coverage.** None, because there is no rule. The two implemented cross-field rules are tested at
both boundaries; the third has neither.

**The first ERT-100/ERT-200 review checked this category and cleared it**, under *Categories with no
findings*: *"Cross-field `app_setting` bounds — checked, and they are handled. The V3 seed comments
defer [two rules] to a repository validator, and `AppSettingMapper.kt:227` `crossFieldErrors()`
implements both. The deferral was honoured."* That is correct and remains correct. It reads the
**header's** two named deferrals; the third rule is asserted in a per-row comment forty lines further
down, as a property of a bound rather than as a deferral, so nothing was there to check against.

**Recommended fix:** add to `crossFieldErrors()` alongside the two that are there —
`extendOnRejectionDays <= absoluteExpiryDays` (the rule V3's comment claims),
`completedGraceDays <= absoluteExpiryDays`, and `idleExpiryDays <= absoluteExpiryDays` (V3 already
reasons about this — "above which the idle clock could never bind" — but the reasoning assumes the
ceiling sits at its own maximum). Each with a code in the existing `setting.<rule>` namespace and
boundary tests matching the two that exist.

Two things to get right while writing it. V3's comment on `extend_on_rejection_days` is currently a
*claim about the cap*; once the rule exists it must point at the validator the way the header's other
two do, or the file still asserts a property the bound does not carry. And architecture §12 has **no
invariant covering `app_settings` bounds at all**, despite invariant 6's `expiresAt` half depending on
them — a row goes in that table with this work. **Folded into ERT-310, reopened.**

### HAR-15 — The append-only guard reads one file, and no invariant covers the audit trail  [Medium]

**Where:** `test/data/repository/ExposedAuditLogTest.kt:145`; `src/data/repository/ExposedAuditLog.kt`;
architecture §12

```kotlin
const val ADAPTER = "src/data/repository/ExposedAuditLog.kt"
val forbidden = listOf("update(", "deleteWhere", "deleteAll", "deleteIgnoreWhere", "upsert", "replace")
forbidden.filter { it in adapterCode() }.shouldBeEmpty()
```

**What.** Two gaps, and together they are the finding.

**The guard is scoped to one file out of nine adapters.** `AuditLogs` carries no visibility
restriction — `AuditEntryMapper.kt` already imports it — so any other file under `src/data/` can call
`AuditLogs.deleteWhere { }` and the sweep sees nothing. `ArchitectureTest` walks `src/domain` and
`src/core` only, so it does not cover `data/` either. This is **HAR-10's shape one epic later**:
HAR-10 was "a guard scoped to `test/contract/`, one directory of nine", widened on the argument that
*"the trap is not particular to contract suites; it is particular to this toolchain."* The same
argument applies verbatim here and was not made.

**And architecture §12 has no row for it.** Invariant 7 covers the *portal* trail — *"Every portal
access is an append-only record | `PortalAccessLogs`; no `last_accessed_at`"* — with both a named
mechanism and a source. `audit_logs`, which ERT-330 built and which §8.10, §8.13 and §12 all depend
on, appears in **no invariant row at all**. The asymmetry is not argued anywhere.

**Impact.** The audit trail's only property that matters is that nothing removes a row. Today that is
a convention plus a one-file sweep, with nothing in the invariant table a reviewer would check
against.

**Reachability.** **ERT-734 — "Purge beyond retention, unless retention is frozen"** — is a ticket
whose entire job is deleting rows, under invariant 8, which is a compliance rule. A purge that also
tidied `audit_logs` would compile, pass the whole suite, and read as reasonable in review. Phase 2's
reopen (`RECORD_REOPENED` exists as an action) and any data-fix repository are the other doors.

**Test coverage.** The guard exists and is well built — it strips comments, and a second test pins the
stripping so the sweep cannot pass vacuously. Only its *scope* is the finding.

**Recommended fix:** move the sweep into `ArchitectureTest` and invert it — **no file in `src/` but
`ExposedAuditLog.kt`, `AuditEntryMapper.kt` and `Tables.kt` may name `AuditLogs` at all**. That is
stronger and simpler than scanning for mutation verbs, which must enumerate every Exposed write API
and would still miss a raw `exec`. Carry the anti-vacuity floor the file's other guards use, and add
the matching invariant row to architecture §12. **Folded into ERT-734.**

### HAR-19 — The settings contract suite cannot compare audit behaviour, because the fake writes no audit row  [Medium]

**Where:** `test/testdata/fake/FakeAppSettingsRepository.kt`;
`test/contract/AppSettingsRepositoryContract.kt`

```kotlin
// FakeAppSettingsRepository.updateLinkPolicy
this.policy = policy
updateCalls += Update(policy, actor)
return Unit.asOk()
```

**What.** ERT-250 exists because "nothing keeps a port, its fake and its adapter in step" (HAR-01).
For `AppSettingsRepository` the adapter's `updateLinkPolicy` does two things — writes the changed rows
**and** writes one audit row in the same transaction — and the fake does one. The contract suite
therefore asserts only the half both implementations share: that a later read returns the new policy.

The fake's KDoc argues carefully for one deliberate divergence — bounds are not enforced, so a bounds
bug in the adapter cannot hide behind a fake that already filtered — and the second ERT-100/200 review
lists that divergence under *"Checked and healthy — do not trade these away"*. **The audit-row
divergence is not argued anywhere**, and it is the one that hides SEC-38: a contract test changing
`pinAttemptsBeforeLockout` would pass on the fake and throw on the adapter, which is precisely the
disagreement ERT-250 was built to surface.

**Impact.** ERT-310's most consequential rule — every settings change is audited with old value, new
value, actor and timestamp (§8.10) — is covered on one implementation only. The port's shape is what
allows it: `updateLinkPolicy` returns `Unit`, so the audit row is not observable through the port, and
the adapter test reads it out of the database directly.

**Reachability.** Now. It is why fifteen `updateLinkPolicy` exercises did not find SEC-38.

**Recommended fix:** two parts. **(1)** Add SEC-38's guard as a **contract** test rather than an adapter
test: *"a change to every settings key in turn — both implementations accept it"*, driven off
`LinkPolicySetting.entries` so it covers all nine by construction and a tenth the day it is added. On
the fake it is trivially green; on the adapter it is the test that fails today. **(2)** Record the
audit-row divergence in the fake's KDoc beside the bounds one, so the next reader knows which
divergences are argued and which are accidental — the distinction the second review relied on.
**Folded into ERT-310, reopened**, with the fake's KDoc half noted against ERT-250.

### HAR-20 — `ReferenceDataRepository` has two fakes, and they disagree about ordering  [Medium]

**Where:** `test/testdata/fake/FakeReferenceDataRepository.kt`; a private `FakeReferenceData` inside
`test/route/hr/ReferenceRoutesTest.kt:175`

**What.** Two in-memory implementations of one port exist in the same test tree, and they behave
differently: the shared fake sorts both list reads by name — the port's stated contract, enforced by
`ReferenceDataRepositoryContract` — while the route test's local fake returns the list as given.

The local fake was correct when written. ERT-350's own carry-forward note explains it: *"ERT-430 will
also want a `FakeReferenceDataRepository` in `test/testdata/fake/`; ERT-350 has only a local fake in its
route test, because a shared fake exists for use-case tests and there is no use case yet."* The shared

`ReferenceRoutesTest` asserts `/api/departments` returns rows "in name order" against a fake that does
not sort, so the route test passes whether or not ordering survives the DTO mapping — the same vacuity
ERT-350 recorded twice ("in name order" against one seeded row) reached through a third door.

**Reachability.** Now, for the vacuity. The divergence itself fires the first time anyone reads the
route test as evidence about ordering.

**Test coverage.** `ReferenceDataRepositoryContract` covers the shared fake against the adapter, which
is right and is why the shared fake sorts. It cannot see a second fake it does not know about.

**Recommended fix:** delete the local fake and use the shared one in `ReferenceRoutesTest`, then widen
`ArchitectureTest`'s port-coverage guard from "every port has a fake" to **"no class outside
`test/testdata/fake/` implements a `domain.port` interface"**. That guard catches this one and the next
one. **Folded into ERT-250**, which owns the port/fake/adapter correspondence and whose guard this
extends.

### SEC-40 — Reference data is seeded-not-managed, and the hand edit that forces has no format guard  [Low]  [A04:2025]

**Where:** `src/data/repository/ExposedReferenceDataRepository.kt`; `resources/db/migration/V1__baseline.sql:37`

```sql
create table departments (id varchar(12) primary key, "name" varchar(128) not null);
```
```kotlin
id = EntityId.of(it[Departments.id].value).orFail("departments.id"),
```

**What.** `EntityId.of` requires **exactly** 12 characters matching `[A-Za-z0-9]{12}`. The column is
`varchar(12)`, which permits anything **up to** 12 — `'FINANCE'`, `'IT'`, or a value with a hyphen.
`orFail` calls `error(...)`, so one such row makes `findDepartments()` throw and `GET /api/departments`
answer 500 **permanently**, blocking the add-hire form entirely.

The route's own `describe { }` says reference data is "**seeded, not managed** in Phase 1 — there is no
create, update or delete." The V2 seed holds exactly **one** department, `'Unassigned'`, with its header
stating that inventing an org chart "would be fiction that later gets treated as fact." So the only way
to add the departments a real deployment needs is a hand-written `insert`, and nothing in the schema
tells the person writing it that the id must be exactly twelve characters of a specific alphabet. V2's
header knows the rule — "each padded to the 12 characters an entity id requires" — but that comment is
in a file the operator adding a department is not editing.

**Impact.** Small blast radius, total within it: one malformed row takes out the whole listing rather
than one entry, and surfaces as a 500 on the add-hire form rather than as anything diagnosable from the
UI. The same applies to `employment_types` and, through `RequirementTemplateMapper`, to
`requirement_templates` — which **Q2's answer will replace wholesale, by hand**.

**Reachability.** The first department a real deployment adds; Q2's answer for the catalogue. Both are
Phase 1 exit items.

**Test coverage.** None. `ExposedReferenceDataRepositoryTest` covers the seeded catalogue and the
cross-table existence cases; no test inserts a short id. `MigrationTest`'s identifier-width sweep is
over the *schema*, not over row values.

**Recommended fix:** a `check (char_length(id) = 12)` constraint on the `varchar(12)` id columns, so the
database refuses the row at insert — where the operator is standing — rather than at read, where a hire
is. Additive, and a migration. **Folded into ERT-1190.** It is a correctness constraint rather than an
access path, so it wants its own line in that ticket rather than joining the index list — the SEC-36
precedent.

### PERF-14 — `linkPolicy()` reads the whole `app_settings` table on every call, uncached  [Low — latent]

**Where:** `src/data/repository/ExposedAppSettingsRepository.kt:93`

```kotlin
private fun JdbcTransaction.storedSettings(): Map<String, StoredSetting> =
    AppSettings.selectAll().associate { it[AppSettings.key] to it.toStoredSetting() }
```

### HAR-18 — A branch in `readStored` that no input can reach, and two unchecked casts  [Info]

## Dispositions

**Nothing in this review was measured by running the suite**, and one claim needs no run: SEC-38 is a
substring match between two string literals quoted in full above. The rest are read from source.

**The most serious finding was not in scope.** SEC-41 surfaced while correcting architecture §4's
stale `Notifier` bullet (C42) — the bullet named the wrong method, and checking which method was right
showed that the right one takes an `AccessPin` and renders it into an email body. It is reported rather
than deferred because it is a P0 control in four documents, and because a review that corrects a
sentence about a rule without checking the rule is the exact failure this project keeps re-filing.

**The sharpest finding in scope is a guard doing exactly what it was written to do.** `refuseCredentials` is a
good control, argued at length in its own KDoc, and it refuses `portal.pin_attempts_before_lockout.old`
for precisely the reason it was built. What no one checked was whether the closed set of keys the
application itself generates could collide with it. That check is one test over an enum, and it is the
deliverable — not the exemption.

**C25 and SEC-38 are one guard and two false-positive classes**, found eleven months apart in project
time and a day apart in wall-clock. C25's disposition — pin the behaviour, do not weaken the tripwire —
was right and stands. SEC-38's is different because the trap is unconditional rather than rare, and
because the colliding key is one this codebase chose rather than one a user typed.

**Two findings exist only because ERT-250 landed.** HAR-19 is a statement about a contract suite that
was unmerged when this review began reading and reached `main` before it was written; HAR-20 is a second
fake that the contract suite makes visible by contrast. That is the argument for a suite per port,
restated one epic later.

**The pattern behind the six contradictions is the pattern the last two reviews named**, and it recurred
in a document that names it: *a statement true when written, not revisited when something beside it
changed.* C40 counts two bindings where there are twelve; C42 says `domain/usecase/` is empty where there
are seven use cases; C39 counts seventeen audit actions where there are twenty-five. The project's answer
— turn the rule into a guard that fails the build — is what SEC-38's and HAR-20's fixes are, and it is
why neither is a patch.
