## Findings

### HAR-09 — Every fake orders text the way H2 does, and production does not  [Medium]

**Where:** `test/testdata/fake/` against `ExposedEmployeeRepository.requirementsOf`;
`resources/db/migration/V7__requirement_sort_order_snapshot.sql`

**What.** Every fake sorts strings with Kotlin's `String.compareTo`, which compares UTF-16 code
units. Every adapter sorts with the database's collation. The first pass called this out as PERF-12's
first instance and ranked it **not measured**, because *"PERF-12's collation divergence cannot be
exhibited on H2 by definition"*. With ERT-260's PostgreSQL job it can be, and it is wider than a
tiebreak:

| `Apple`, `Zebra`, `_Underscore`, `apple` ascending | Result |
|---|---|
| Kotlin `String.compareTo` — every fake | `Apple`, `Zebra`, `_Underscore`, `apple` |
| H2 in PostgreSQL mode | `Apple`, `Zebra`, `_Underscore`, `apple` |
| **PostgreSQL 17, `en_US.UTF-8`** | **`apple`, `Apple`, `_Underscore`, `Zebra`** |

PostgreSQL weights letters before case and disregards the underscore's code point entirely. **The
fakes agree with the test engine and disagree with the production engine.**

`ExposedRequirementTemplateRepository` states this caveat and argues it cannot fire, because the
catalogue's `sort_order` runs 1..14 with each value used once — the name is a tiebreaker for a tie
that does not occur. **The same argument was never made for `employee_requirements.name_snapshot`**,
and cannot be: `sort_order_snapshot` carries `default(0)`, which is what let V7 apply to a populated
table at all. V7's own header warns that a writer inheriting that default *"puts every row at one
value and collapses the order back to name"* — and name order is precisely what the two engines
disagree about.

**Impact.** A hire's checklist renders in one order in every test that has ever run and a different
order on their phone, for any two requirements sharing a `sort_order_snapshot` whose names differ in
case or punctuation. §5 makes checklist order a product decision; this makes it an engine decision.

**Reachability.** Not reachable through `CreateHireUseCase` today, because ERT-432 copies
`sort_order` from a catalogue where it is unique. Reachable the moment anything writes a requirement
row without a sort order — which is the exact path V7's header exists to warn about — or the moment
Q2's real checklist introduces a tie.

**Test coverage.** `test/data/db/CollationTest.kt`, added by ERT-260, **pins** the divergence
engine-aware rather than asserting it away, on the C25/C27 precedent. The safe subset — Title Case
names differing in their first letter, which is what Appendix A actually holds — is asserted to
resolve identically on both, so the pin cannot be read as "ordering is arbitrary".

**Recommended fix:** a collation decision in a migration — `collate "C"` on `name_snapshot`, or an
ordering key that is not text. **Folded into ERT-1190**, which is already the migration that is
happening anyway and which the first pass used the same argument to load TASK-26 onto.

### HAR-10 — A test class named for anything but the scan is silently not run  [Medium]  *(Fixed here)*

**Where:** `test/ArchitectureTest.kt`; Amper's `JvmTestTask`

**What.** Amper runs the suite with `--scan-class-path` and passes **no** `--include-classname`, so
JUnit's own default filter applies: `^(Test.*|.+[.$]Test.*|.*Tests?)$`. A class named
`EmployeeRepositoryContractSuite` is never instantiated. It contributes zero tests, raises nothing,
and neither `--fail-if-no-tests` nor CI's `require_tests: true` notices — both are **whole-run**
floors, satisfied as long as anything anywhere ran.

This is the trap architecture §10 already documents for Kotest specs, reached through a different
door, and it is **the specific risk of the shape ERT-250 chose**: shared tests on an abstract base,
one concrete subclass per implementation. The base is correctly skipped; a misnamed subclass is
skipped identically, and a contract suite that silently runs against the fake alone is worse than
none — it asserts agreement while testing one side.

**Impact.** None today: every class holding a `@Test` is correctly named, verified by sweep.

**Reachability.** The next test class anyone adds.

**Test coverage.** ERT-250 added the guard and **scoped it to `test/contract/`** — one directory of
nine. The trap is not particular to contract suites; it is particular to this toolchain.

**Fixed here**, because a guard that covers a ninth of the surface is the kind of half-measure this
project's own register keeps re-filing: the guard now sweeps all of `test/`, matches only classes
that actually carry a `@Test`, and carries the anti-vacuity floor the file's other guards use. It
was verified by adding a misnamed class and watching the build fail.

### HAR-11 — `junit-jupiter-params` is on the test classpath only because of MockK  [Medium]

**Where:** `module.yaml` `test-dependencies`; `mockk-jvm-1.14.5.module`

**What.** `module.yaml` declares four test dependencies and none of them is `junit-jupiter-params`.
It arrives anyway: `mockk-jvm` depends on the `org.junit.jupiter:junit-jupiter` **aggregator**, whose
POM pulls `junit-jupiter-api`, `junit-jupiter-engine` **and** `junit-jupiter-params`.
`kotlin-test-junit5` declares the first and third but not params; `ktor-server-test-host` declares no
JUnit at all.

**Impact.** Nothing uses it today, so nothing breaks today. The finding is that a capability the
suite appears to have is held by a dependency **ERT-1140 is explicitly deciding whether to delete** —
HAR-07 recorded that MockK is declared and used by zero tests. Anyone reaching for
`@ParameterizedTest` would be building on a transitive dependency of a library scheduled for review,
and the failure would land on whoever removes MockK rather than on whoever used it.

There is a second, sharper version of this that ERT-250 met directly: `@ParameterizedTest` was one of
the three candidate shapes for the contract suite, and **this is one of the reasons it was
rejected**. That reasoning is recorded in ERT-250's block, where the next person considering it will
find it.

**Reachability.** The first test to use `@ParameterizedTest`, or the ERT-1140 session, whichever
comes first.

**Test coverage.** None, and none is natural — a dependency's provenance is not a behaviour.

**Recommended fix:** **folded into ERT-1140**, which already owns the MockK question. If MockK stays,
declare `junit-jupiter-params` explicitly so the capability is owned rather than inherited. If MockK
goes, say in the same commit that `@ParameterizedTest` goes with it.

### SEC-36 — Nothing stops a hire holding the same requirement twice  [Low]  [A04:2025]

**Where:** `resources/db/migration/V1__baseline.sql:45`; `ExposedEmployeeRepository.saveRequirements`

```sql
create table employee_requirements (id varchar(12) primary key, employee_id varchar(8) not null,
  template_id varchar(12) not null, ... )
```

**What.** Two foreign keys and no uniqueness. There is no constraint on
`(employee_id, template_id)`, and `saveRequirements` is read-then-insert-or-update keyed on `id`
**alone** — so the same template can be snapshotted against one hire any number of times, each under
a fresh `EntityId`, and the database will take every one.

**Impact.** A duplicated requirement row is counted twice by §6.5's progress arithmetic, so a hire
reads as "2 of 15" against a checklist of fourteen and can never reach complete. It also renders
twice on the portal. Contrast `upload_links.token_hash` and `users.email`, both of which carry the
constraint that makes the equivalent mistake unrepresentable.

**Reachability.** Not reachable today — `CreateHireUseCase` builds the set once, from a catalogue
read that returns each template once. Reachable from any second writer: ERT-1030's reissue path,
Phase 2's reopen, or a retry that re-runs the snapshot after a partial failure. `saveRequirements`
runs all rows in one transaction, so a partial write is not the path; a *re-run* is.

**Test coverage.** None. No test asserts a hire cannot hold a requirement twice, on either
implementation — the contract suite asserts ordering and not-found, not this.

**Recommended fix:** a unique index on `(employee_id, template_id)`. **Folded into ERT-1190** — it is
a schema change, it is additive, and that is the migration already happening. Note it is *not* an
index-for-speed finding, so it needs its own line in that ticket rather than joining the list of
access paths.

### SEC-37 — `OutboxNotifier` reports a cancelled coroutine as a delivery failure  [Low]  [A09:2025]

**Where:** `src/data/notify/OutboxNotifier.kt:270`

```kotlin
): DeliveryResult = runCatching {
    …
}.getOrElse { failure -> DeliveryResult.Failed(failure::class.simpleName ?: "write failed") }
```

**What.** `runCatching` catches `Throwable`, which includes `CancellationException`. A request
cancelled while the outbox insert is in flight therefore returns `DeliveryResult.Failed("CancellationException")`
rather than propagating the cancellation, and the calling coroutine carries on as though a delivery
had merely failed.

The `runCatching` is correct and must stay — §8.1 requires the hire to survive a failed invitation,
and ERT-250's contract suite now asserts on both implementations that no send ever throws. The
finding is only that cancellation is not a delivery failure.

**Impact.** Small and real: `CreateHireUseCase` would record a delivery failure and surface a retry
action to HR for a request nobody is waiting for, and structured concurrency loses a cancellation it
is entitled to. On Cloud Run, a client disconnect or an instance drain is the realistic producer.

**Reachability.** Any cancelled request that reaches the notifier. Not reachable today — no route
calls it yet; ERT-434 is the ticket that makes it reachable.

**Test coverage.** None, and the new contract test would not catch it: it asserts a failure is a
value, which is exactly what this does.

**Recommended fix:** re-throw `CancellationException` before the `getOrElse`, or catch `Exception`
rather than `Throwable`. **Folded into ERT-434**, which is the next ticket and already owns the
question of how a failed queue-insert becomes visible.

### PERF-13 — Twelve of fourteen adapter reads have no `limit`  [Low — latent]

**Where:** every adapter in `src/data/repository/`

**What.** `limit` appears in exactly two places in the whole data layer:
`ExposedUploadLinkRepository.findActiveForEmployee` (`limit(1)`) and `OutboxNotifier.pending`
(`limit`, default 50). `findAll`, `findFor`, `requirementsOf`, `findActiveByEmail`, `forEmployee`,
`findDepartments`, `findEmploymentTypes` and the catalogue reads are all unbounded.

**What this is and is not.** Most are bounded by the domain and are fine: fourteen requirements per
hire, fourteen templates, a handful of departments, a handful of HR accounts. Two are not.
`AuditLog.findFor` reads an append-only table with **no ceiling at all** — §8.12 renders the history
of one entity, and an entity that has been edited for two years returns two years of rows.
`findActiveByEmail` is bounded by how many hires share an address, which SEC-11 exists because it is
not always one.

**Expected win.** None today; there is no production data and no route reads either of them yet. It
is ranked Low and latent for the reason PERF-10 is ranked the way it is: the cost of a page size is
near zero before there are rows and a conversation about locks after.

**Recommended fix:** a page size on the two that grow without bound, taken with the ticket that first
renders them — **ERT-520** for the audit history, **ERT-510** for the duplicate list. Recorded in
both rather than given a ticket of its own, because a limit with no renderer is a guess at a page
size.

### HAR-14 — `OutboxNotifier.retry` reads and writes in two transactions  [Info]

**Where:** `src/data/notify/OutboxNotifier.kt` — `retry`

**What.** `retry` calls `find(id)` — which opens its own transaction — checks
`entry.kind.storesBody`, and then opens a second transaction to update. A row deleted or changed
between the two is not guarded; the `check` is made against state that may no longer hold when the
write lands.

**Impact.** Negligible and stated for completeness. `retry` has no caller until ERT-1010, there is
one writer, and the worst outcome is a `check` message naming a row that has since changed. Contrast
`markFailed`, which reads and increments **inside one transaction**, with a comment saying why — so
the pattern is understood in the same file and not applied here.

**Recommended fix:** fold the `find` into the same `factory.transaction { }` the update uses.
Recorded against **ERT-1010**, which is the ticket that gives `retry` its first caller.

### C37 — Three comments still say the invitation is the only body-less notification  [Contradiction]

**Where:** `src/data/notify/OutboxNotifier.kt:316`; `src/data/db/table/Tables.kt:283`, `:301`

```kotlin
// OutboxNotifier.kt:316
* [body] is null for `INVITATION` by rule and for nothing else — see [OutboxNotifier]'s own note.
// Tables.kt:301
/** Null for `INVITATION`, always. See this table's own note. */
// Tables.kt:283
* **[recipient] is nullable because two of the seven `Notifier` methods take no address.**
```

`NotificationKind` has **eight** entries and **two** with `storesBody = false` — `INVITATION` and
`RECOVERY_PIN`, the latter added when C23 split the port so `sendInvitation` takes no PIN. `Notifier`

the comment, not the enum.

**Disposition: closed as documentation**, with a dated note. It is the C33 shape — a KDoc that was
true when written and was not revisited when the thing beside it changed — one epic later.

- **The mutation pass is now a habit rather than an event, and it earned its keep twice.** ERT-250's
  eighth divergence and the `singleOrNull` equivalent mutant were both found by it and by nothing

## Dispositions

**Three claims the first pass could not measure, now measured.** PERF-12's collation divergence is
real and larger than assumed (HAR-09). HAR-05's V4 defect is a **hard failure**, not the silent
discard the first pass offered as the likelier of two. And the PostgreSQL job's own value is now a
number rather than an argument: 48.9 s against 14.4 s, zero failures in the existing suite.

**Two findings exist only because ERT-250 built the instruments that found them.** The eighth
divergence came from the mutation pass; the seventh came from writing a contract for a port whose
divergence nobody suspected. That is the argument for a suite per port rather than a patch per known
defect, restated as evidence.

**The pattern behind most of this review is the pattern behind the last one**, and it is worth
naming a second time because it recurred inside the document that named it: *a statement true when
written, not revisited when something beside it changed.* C35 is that failure applied to a
disposition list; C36 and C37 to a version and a comment. The project's answer — turn the rule into
a guard that fails the build — worked again here: the port-coverage guard closed the count that C9
and C30 could not, and the discovery guard closes a trap that had no name before this branch.
