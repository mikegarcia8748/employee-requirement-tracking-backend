## Findings

### SEC-31 — `DATABASE_USER` defaults to `sa` and `DATABASE_PASSWORD` is the one reader that accepts blank  [Low]  [A02:2025]

**Where:** `src/data/db/DatabaseFactory.kt:174-175` — `DatabaseConfig.fromEnvironment()`

```kotlin
user = user?.takeUnless(String::isBlank) ?: "sa",
password = password ?: "",
```

**What:** ERT-160 Decided-2 established the house idiom — *"`?:` catches `null` but not `""`.
Sourcing a `.env` copied from `.env.example` supplies exactly the empty string"* — and every other
reader in `src/` follows it. `DATABASE_PASSWORD` is the single exception: a blank password is
accepted as a configured one. Beside it, a blank `DATABASE_USER` resolves to `"sa"`, which is the H2
default carried into the PostgreSQL path.

SEC-18 fixed `DATABASE_URL` in ERT-1241 and left the credential pair in the same function untouched —
and `sa` with an empty password is the exact credential SEC-18's own impact paragraph named.

**Impact:** a production deploy that keeps `DATABASE_URL` and loses the credentials attempts
`jdbc:postgresql://…` as `sa` with no password. PostgreSQL refuses it, so this **fails closed** — the
impact is a confusing startup failure that names a Hikari error rather than the missing variable, not
an open database. Filed at Low for that reason.

**Also in this function, and worth one line of the same fix:** `driverClassName` is chosen by
`resolved.startsWith("jdbc:postgresql")`, with `org.h2.Driver` as the fallback for everything else.
A typo like `jdbc:postgres://` therefore loads the H2 driver against a PostgreSQL URL and fails with
a driver error rather than naming the typo.

**Reachability:** every deploy with a blank or missing credential variable.

**Test coverage:** `DatabaseConfigTest` covers the URL rules thoroughly — including
`a blank database url - is treated as unset`. There is no equivalent for the user or the password,
which is why the inconsistency survived.

**Recommended fix:** `takeUnless(String::isBlank)` on both, and outside dev require both when the URL
names PostgreSQL — the same shape as `JWT_SECRET`. Make the driver fallback explicit rather than an
`else`.

### SEC-32 — Nothing ever runs this application in production mode  [Medium]  [A02:2025]

**Where:** `module.yaml` — `settings.jvm.test.extraEnvironment: APP_ENV: dev`;
`.github/workflows/build.yml` — `docker run -d --name smoke -p 18080:8080 -e APP_ENV=dev ert:pr`

**What:** the whole test JVM runs as dev, and CI's container smoke test passes `-e APP_ENV=dev`
explicitly. Every fail-closed control this project built — `JWT_SECRET` required, `TOKEN_PEPPER`
required and ≥ 32 characters, `DATABASE_URL` required, HR bootstrap refusal, `/swagger` and
`/metrics` gating — is verified **only as a pure function** with the environment handed in as a
parameter.

That parameterisation was the right call and it is what made the rules testable at all; ERT-190 and
ERT-150 both record the reason (*"a JVM test cannot unset an environment variable in its own
process"*). What is missing is the other half, and ERT-160's own scope note says so plainly:

> *"**What is proven is that the refusal fires, not that it aborts the boot** — the boot path is
> covered only by the eager resolution in `configureKoin()` being on the same line as `install(Koin)`.
> Verify the real thing by hand with `APP_ENV=prod JWT_SECRET=… ./kotlin run`."*

Five controls rest on that hand-verification, and a hand-verification is a control that runs when
somebody remembers — which is the argument ERT-1160 already made for having CI at all.

**Impact:** a refactor that moves `getKoin().get<TokenDigest>()` out of `configureKoin()`, reorders
`rootModule()`, or wraps a `check()` in a `runCatching` would leave every pure-function test green
and ship a deployment that boots permissively. This is the same defect class as SEC-17, which is the
one this project rates most highly: one variable, no signal, permissive by default.

**Reachability:** not an attack path. It is the absence of the test that would catch the next SEC-17.

**Test coverage:** none, and none is possible in-process. It has to be a second process.

**Recommended fix:** the CI image job **already runs a container**. Add a second `docker run` at
`APP_ENV=production` with nothing else set, and assert the container exits non-zero and logs the
refusal. That is one step, no new infrastructure, and it converts five hand-verification notes into a
guard. Run the same check for each of the five controls in turn, or assert on the first refusal and
name the rest in the runbook.

### SEC-33 — Every audit row records the load balancer's address, not the caller's  [Medium]  [A09:2025]

**Where:** `src/route/hr/AuthRoutes.kt:56-59`

```kotlin
// The peer address, not a forwarded header. `X-Forwarded-For` is caller-controlled
ip = call.request.local.remoteAddress,
```

**What:** the reasoning in that comment is correct for a server a client reaches directly — a
caller-controlled header must not be trusted as identity. It is wrong for the deployment ERT-1200
chose. On Cloud Run the peer is always the Google front end, so `local.remoteAddress` is an internal
Google address on every request, from every caller.

ERT-190's acceptance criterion reads *"Given any sign-in attempt, then an audit row records outcome,
actor and source IP."* The row is written and the column is populated. The value is the same for
everyone.

**Impact:** three controls that are already planned rest on this field and would rest on a constant.

- **SEC-24 / ERT-1185** proposes alerting on a burst of `SIGN_IN_FAILED`. It could not tell a burst
  from one source apart from ordinary Monday-morning traffic.
- **SEC-19 / ERT-1170** proposes a DB-backed attempt counter. If it is ever keyed on address rather
  than on the attempted email, it limits the load balancer — which means it limits every HR user at
  once, and the attacker not at all.
- **ERT-610 will inherit the same call** for `PortalAccessTrail`. `distinctIpsFor` is §6.6's anomaly
  signal — *"one link, many addresses"* — and it would see exactly one address for every hire, so the
  control reports nothing, forever, without failing.

`AuthenticateHrUserUseCase` is correct throughout: a `SIGN_IN_FAILED` row never names the account,
so the trail is not an oracle. The defect is only that the one field meant to identify the caller
does not.

**Reachability:** every request, once deployed behind Cloud Run. **Not measured** — this follows from
the deployment shape rather than from an observed row, and the confirmation is one `select ip from
audit_logs` against UAT.

**Test coverage:** none, and a route test cannot have any — `testApplication` has no proxy in front of
it, so both the current code and the fix would look identical.

**Recommended fix:** not "trust `X-Forwarded-For`". Install Ktor's `ForwardedHeaders` with a decided
trusted-hop count and read `call.request.origin.remoteHost`, so the value comes from a known position
in the chain rather than from whatever the caller appended. Decide it **once**, in a helper both
`AuthRoutes` and ERT-610 call, because the second call site is where a per-route decision diverges.
Note while there that `ip varchar(64)` must hold one address, not a header — an `X-Forwarded-For`
chain will exceed it.

### SEC-34 — `AppError.Conflict` is the one error whose message reaches the wire unguarded  [Low]  [A02:2025]

**Where:** `src/route/mapper/AppErrorMapper.kt` — `toApiError()`

```kotlin
is AppError.Conflict -> ApiError(code = code, message = detail)
```

**What:** ERT-140 Decided-2 and ERT-190 made `Denied`, `AuthenticationFailed` and `Forbidden`
field-less `data object`s *precisely* so that two call sites cannot render two different bodies —
*"differing responses are unrepresentable"*. Every other case routes its message through
`messageFor(code)`, a closed `when` over known strings. `Conflict` alone carries a free-text `detail`
straight to the client.

**Impact:** none today — every construction site passes a static literal, and they were all read.
The finding is that the property the other three cases hold *structurally* is held here only by
convention, in the one case where the value is a caller-influenced string. The realistic failure is
the ordinary one: `Conflict("upload_locked", "Requirement ${requirement.nameSnapshot} is locked")` on
a portal path, which reads as helpful in review and puts a snapshot name into a response the
write-mostly rule exists to keep bare.

**Reachability:** no current call site does this.

**Test coverage:** `ErrorMappingTest` asserts a conflict returns 409. Nothing asserts what its
message may contain.

**Recommended fix:** route `Conflict` through `messageFor(code)` like everything else and keep
`detail` server-side, or — if a conflict genuinely needs to say which thing conflicted — carry it as
an `ApiErrorDetail` with a `field`, which is the slot the envelope already has for exactly this.
Either way it becomes a shape rather than a habit.

### SEC-35 — The portal-path log redaction is a literal prefix in one `format` block  [Low today; gates ERT-630]  [A09:2025]

**Where:** `src/plugin/Monitoring.kt` — `install(CallLogging) { format { … } }`

```kotlin
val safePath = if (path.startsWith("/api/portal/")) "/api/portal/[redacted]" else path
```

**What:** SEC-21 / **ERT-1110** already owns the two `StatusPages` call sites that bypass this. What
is not recorded anywhere is that the redaction itself is narrow in two further ways: it is an exact
prefix, so a portal route mounted at any other path is logged in full; and it reads
`call.request.path()`, which excludes the query string, so a token that ever arrives as a parameter
is outside its reach.

Nothing ties `src/route/portal/` to that prefix. `ArchitectureTest` has a guard for what a portal DTO
may declare and what a portal route may import, and none for where a portal route mounts.

**Impact:** identical to SEC-21's, through a different door. Since 2026-09-16 the token is the whole
authentication factor, so a portal path in a log file is a live credential in a log file.

**Reachability:** not reachable today. Reachable the day ERT-630 merges.

**Test coverage:** `RequestCorrelationTest` covers that the *request id* contains no part of a token.
Nothing covers the access-log line itself against a non-conforming path.

**Disposition: fold into ERT-1110**, which already argues that the deliverable is the guard rather
than the two-line fix. The guard it needs grows one assertion: every route mounted under
`src/route/portal/` sits beneath the prefix the redaction matches.

### PERF-10 — The baseline schema indexes almost none of its foreign keys or query predicates  [High expected win — latent]

**Where:** `resources/db/migration/V1__baseline.sql`

**Mechanism.** Neither PostgreSQL nor Exposed creates an index for a foreign key. `V1` declares
thirteen tables and creates exactly two plain indexes — `employees_email` and `audit_logs_entity_id` —
plus the two `token_hash` uniques and the primary keys. Every other access path is a sequential scan.

Unindexed, and on a path something already written or already ticketed will take:

| Column(s) | Read by | Grows with |
|---|---|---|
| `employee_requirements.employee_id` | `requirementsOf` — the checklist read | ~14 rows per hire |
| `submissions.employee_requirement_id` | the per-requirement version history | uploads |
| `upload_links.employee_id` | `findActiveForEmployee` | hires |
| `upload_links.status`, `expires_at`, `idle_expires_at` | **ERT-1020's expiry sweep**, which scans for work | hires |
| `portal_sessions.upload_link_id` | `findActiveForLink` | sessions |
| **`portal_access_logs.upload_link_id` + `timestamp`** | **§6.6's `countRecentFailures`** | **every portal request, forever** |
| `audit_logs.timestamp`, `actor_user_id` | §8.13's exception report | every action, forever |
| `employees.department_id`, `employment_type_id`, `packet_status` | ERT-510's HR list | hires |

**The contrast is the evidence that this is an omission rather than a house style.**
`V6__notification_outbox.sql` (ERT-440) creates an index on its foreign key **and** on the column its
poller filters by. A later ticket knew to do it; the baseline did not.

**The `portal_access_logs` row is the one to read twice.** It is append-only by design, it is the
fastest-growing table in the schema, and `countRecentFailures(linkId, since)` is the query that
decides §6.6's lockout and auto-suspend. That makes it a security control whose cost rises with the
log it reads, on the unauthenticated portal path — the same shape as SEC-19, reached from the schema
instead of from the algorithm.

**Evidence — static, and deliberately not guessed at.** No production data exists, so no plan can be
captured. What can be said without measuring: at ~14 requirement rows per hire, the checklist read
scans the whole table at every portal open, and the trail has no ceiling at all.

**Expected win.** High and latent. The reason to act **now** rather than when it hurts: an index is a
pure addition, safe under architecture §14's backward-compatibility rule, and cheap against an empty
table. `CREATE INDEX` against a large table is a different operation with a different conversation
about locks.

**Risk.** Write amplification on `portal_access_logs`, which is insert-only and high-volume. That is
the one place to pick the index deliberately — `(upload_link_id, timestamp)` composite rather than two
singles — rather than indexing every column named above.

**Lands with:** TASK-26 from the 2026-09-17 bottleneck audit, which already scopes the `lower(email)`
functional index to *"the next migration that happens anyway"*. This is that migration.

### PERF-11 — `/metrics` exists, and the pool it most needs to report is not wired to it  [Medium expected win — enabling]

**Where:** `src/data/db/DatabaseFactory.kt` — `connect()`'s `HikariConfig`;
`src/plugin/Monitoring.kt` — `attributes.put(MeterRegistryKey, registry)`

**Mechanism.** The `HikariConfig` sets `poolName`, five timings and `validate()`, and no
`metricRegistry`. So Hikari's `active` / `idle` / `pending` gauges — the two numbers that decide
whether **PERF-05** is real — are absent from the `PrometheusMeterRegistry` that `/metrics` serves.

The blocker is an ERT-100 decision rather than an oversight: `configureMonitoring()` owns the registry
and stores it in `Application.attributes`, not in Koin. `DatabaseFactory` is a Koin `single` and
cannot reach it. **ERT-195's Out of scope names the identical blocker** for a different improvement:

> *"A Micrometer `Timer` per use case… Blocked today: the registry lives in `Application.attributes`
> under `MeterRegistryKey`, not in Koin, so a Koin-resolved tracer cannot reach it."*

One placement decision now blocks two separate improvements, and each ticket recorded it as its own
local constraint.

**Evidence.** Static. `grep metricRegistry src/` returns nothing.

**Expected win.** None directly — it produces no speedup. Ranked Medium because it is the prerequisite
the 2026-09-17 bottleneck audit's **TASK-22** could not name a fix for, and PERF-05 stays a hypothesis
until it lands.

**Risk.** Moving the registry into `coreModule` as a `single` and passing it to `configureMonitoring()`
must not change what `/metrics` serves or how it is gated — ERT-150's decision that `Monitoring.kt`
mounts the route, because the gate needs `plugin/` and the arrow does not reverse, is unaffected and
should stay. `MetricsRoutesTest` assembles three plugins and no Koin; keep that property, which means
the registry stays a parameter with a default rather than a container read.

### PERF-12 — Nothing in CI or the suite ever runs against PostgreSQL  [Medium expected win — enabling, latent]

**Where:** `docs/backlog/ERT-200-test-harness.md:292` — ERT-240's Out of scope;
`.github/workflows/build.yml`

**Mechanism.** `RepositoryTestBase` runs H2 in PostgreSQL mode, which was the right call and is
argued honestly in the class KDoc. ERT-240 then deferred the real thing:

> *"A Postgres CI job. Worth adding before launch; not a Phase 0 blocker."*

**With no ticket number.** That is the exact pattern this project's own roadmap names as the lesson of
E5, E6 and C22 — *"a gap without a number is invisible"* — applied to everything except the test
harness. CI runs `./kotlin build`, `./kotlin test`, a Java-21 bytecode check, a secret scan and a
container smoke test **on H2**. PostgreSQL appears nowhere.

**Evidence — three instances are already latent, not hypothetical:**

- **Collation.** Every fake orders text with Kotlin's `String.compareTo` (UTF-16 code units); every
  adapter orders with the database's collation. Identical under H2, divergent under a PostgreSQL
  locale that weights case and punctuation differently. `ExposedRequirementTemplateRepository` states
  this caveat and argues it cannot fire, because `sort_order` runs 1..14 with no ties. The same
  caveat is **not** stated for `EmployeeRequirements.nameSnapshot`, where `sort_order_snapshot`
  carries `default(0)` — so ties there are ordinary, and the tiebreak that decides a hire's checklist
  order is the one nobody argued about.
- **Expression indexes.** H2 rejects them, which is why `V4__hr_users.sql` uses a `CHECK` plus a plain
  `UNIQUE` instead of `create unique index on users (lower(email))`. That substitution is strictly
  stronger and was a good outcome — but it was found by an H2 failure, not by the portability sweep,
  and `MigrationTest`'s own comment says so: *"it is on neither list… this is a proxy and the H2 run
  is what actually found that one."*
- **Identifier widths.** ERT-180 records that the drift test cannot see them at all, because H2
  reports every `VARCHAR(n)` as equivalent to every `VARCHAR(m)`. A dedicated column-width sweep
  exists because of it.

**Expected win.** None in latency. It is ranked Medium because it is what makes several other findings
checkable, and because "H2 is not PostgreSQL" is currently a sentence in a KDoc rather than a job.

**Risk.** A Postgres service container adds perhaps 30 s to CI and a second `DATABASE_URL` path
through `RepositoryTestBase`. Keep H2 as the default so the local loop stays fast and Docker stays
optional, exactly as ERT-240 intended — the Postgres run is an additional job, not a replacement.

### HAR-01 — Nothing keeps a port, its fake and its adapter in step, and six divergences are live  [High]

**Where:** `test/testdata/fake/` against `src/data/repository/`

**What:** the correctness argument for the whole use-case suite is that a fake and its adapter agree.
`ExposedUploadLinkRepository`'s own KDoc states it: a use case that passes against fakes and behaves
differently against SQL is the failure this harness exists to prevent. There is no mechanism enforcing
it — no shared contract test, no guard, nothing but whoever last touched the adapter remembering to
touch the fake.

Six divergences, each verified in both files:

| | Fake | Adapter |
|---|---|---|
| **a** | `FakeEmployeeRepository.findActiveByEmail:70` — no ordering, returns `LinkedHashMap` insertion order | `orderBy(createdAt ASC, id ASC)`, with a test added **in review** because SEC-11's duplicate list must not reshuffle between two reads of the same page |
| **b** | `FakeHrUserRepository.save:56` — a plain map put, no uniqueness | `users_email_unique` + `users_email_is_lowercase`, with three repository tests asserting they bite |
| **c** | `FakeHrUserRepository.findByEmail:46` — `firstOrNull` | `singleOrNull()`, which returns **null** when more than one row matches |
| **d** | `FakeAuditLog.findFor:34` — no ordering | `orderBy(timestamp ASC, id ASC)`, with a test |
| **e** | `FakeUploadLinkRepository.given:71` — a plain map put | the unique index — and the fake's own **constructor** and **`save`** both refuse a duplicate `token_hash` and explain at length why. `given` is the unguarded third door into the same state |
| **f** | `FakeUploadLinkRepository.findActiveForEmployee` — `maxByOrNull`, which returns the first maximal element in iteration order | `orderBy(issuedAt DESC, id DESC).limit(1)`, with the tiebreak named in the KDoc |

**Impact.** (b) and (c) compose into the sharpest one: the fake permits two accounts sharing an
address and then signs the first of them in, while the adapter finds two rows and returns **null**. A
fake-backed sign-in test can therefore be green in a state where production refuses every sign-in for
that address. `CreateHrUserUseCase:86` guards duplicates and says it is belt-and-braces with the
index — but that guard is the thing under test, and removing it would leave
`HrUserAdministrationTest` green.

(f) is the one most likely to fire next, and for a reason particular to this harness: every builder
defaults `issuedAt` to `FixedClock.DEFAULT`, so two links issued in the same instant is not an edge
case here — it is what you get unless a test goes out of its way. `FakesTest`'s ordering test sets
them a day apart and so never reaches the tie the adapter's KDoc exists to describe.

(a) and (d) are latent in the same way: `CreateHireUseCase:228` reads only `duplicates.isEmpty()`
today, and `findFor` has no caller yet. Both become live the moment ERT-450 or ERT-520 renders a list.

**Reachability:** every use-case test written against these five fakes.

**Test coverage:** each *adapter* has a test for its own ordering or constraint. No test compares the
two implementations, which is the gap.

**Recommended fix:** one contract-test suite per port, parameterised over both implementations and
run twice. It closes all six at once and every future instance, and it is the only fix that does —
patching the six leaves the seventh to whoever writes the next adapter. `PortalSessionRepository`,
`SubmissionRepository`, `PortalAccessTrail` and `DocumentStorage` have no adapter yet, so their
suites run against the fake alone until ERT-610/620/720 arrive and then bind the adapter into a
harness that already exists.

### HAR-02 — `FakeNotifier` models a failure mode `OutboxNotifier` structurally cannot produce  [Medium]

**Where:** `test/testdata/fake/FakeNotifierTest.kt:170` against
`src/data/notify/OutboxNotifier.kt:270`

```kotlin
// OutboxNotifier — every failure becomes a value, none becomes a throw
): DeliveryResult = runCatching {
    factory.transaction { NotificationOutbox.insert { … } }
    DeliveryResult.Sent
}.getOrElse { failure -> DeliveryResult.Failed(failure::class.simpleName ?: "write failed") }
```

```kotlin
// FakeNotifierTest — asserts the opposite path exists
fun `fake notifier - the notifier itself throws - is a different path from a failed delivery`()
```

**What:** §8.1 requires that a hire survives a delivery failure, and `OutboxNotifier` implements that
by wrapping the entire write in `runCatching` — an unreachable database, a foreign-key violation on
`employee_id`, anything at all becomes `DeliveryResult.Failed`. It does not throw. `FakeFailure`'s own
KDoc warns against exactly this class of mistake in the mirror direction: *"a fake that returned
`DomainResult.Err` would be modelling a path the real adapter does not have."*

**Impact:** a use case hardened against a throwing notifier is hardened against nothing, and the test
proving it is hardened proves nothing. The worse direction is a use case that correctly ignores the
impossible throw and is then made to look broken by a fake-backed test.

**A second half, and it is the more consequential one.** `FakeNotifier` records the failed attempt
and exposes it as `failed`, so a test can assert that a failure is *visible*. `OutboxNotifier` returns
`Failed` and writes **nothing** — the insert is what failed. But `NotificationOutbox`'s own KDoc says
§8.1's delivery-failure indicator is *"derived from the latest row for a hire"*. So the indicator
cannot see a queue-insert failure at all, and the fake makes a property assertable that production

### HAR-04 — `PortalSession` has no `tokenHash`; the column is `NOT NULL UNIQUE`  [Medium — surfaces in ERT-620]

**Where:** `src/domain/model/PortalSession.kt:12-19` against `src/data/db/table/Tables.kt:207` and
`src/domain/port/Repositories.kt:203`

```kotlin
data class PortalSession(
    val id: EntityId, val uploadLinkId: EntityId, val startedAt: Instant,
    val expiresAt: Instant, val ip: String, val userAgent: String, val endedAt: Instant?,
)
```
```kotlin
val tokenHash = varchar("token_hash", 256).uniqueIndex()   // not nullable
```
```kotlin
suspend fun save(session: PortalSession): PortalSession
```

**What:** ERT-620 is not unaware of this. Its Description says the session token is *"stored as an
ERT-160 digest in `portal_sessions.token_hash`"*, and its Files list already says `Repositories.kt`
must change because *"`findActive` takes a session id today; it must resolve by token digest"*. That
is one half of the port change. The other half has no slot anywhere: the digest has to reach `save`,
and neither the model nor the signature can carry it.

ERT-120's acceptance criterion #2 added the column, and the reasoning was right and is worth
keeping:

> *"Given `portal_sessions`, then it carries a unique `token_hash` column. The table as defined today
> has none, so a session cookie would have to carry the primary key — storing live session bearer
> tokens in plaintext. Adding the column now is free; adding it later is a migration plus a forced
> logout of everyone mid-upload."*

The column landed. The **domain model and the port did not grow the field**, so
`ExposedPortalSessionRepository.save(session)` has nothing to put in a `NOT NULL` column and the
insert cannot be written. The goal the criterion states — a session cookie that is not the primary key
— is unreachable through the port as it stands.

**Impact:** ERT-620 discovers it as a compile error at the moment it writes the adapter, having
planned a different port change. The decision itself is small but real: does `PortalSession` carry
the digest (consistent with `UploadLink.tokenHash`, though it puts a credential derivative in a model
the portal read path handles), or does `save` take it as a second parameter (consistent with
`findByTokenHash` taking a hash, and with `Notifier.sendRecoveryPin` being the only method that
accepts an `AccessPin`)? Filed at **Medium rather than High** because ERT-620 is Not started and
already expects to change this port — the finding is that its Files list names one half of that
change, and the model gap is recorded nowhere at all.

**Why 689 tests do not notice:** `FakePortalSessionRepository` mirrors the model, and there is no
column for it to fill. The schema-drift test compares `Tables.kt` to the SQL and passes, because those
two *do* agree — it is the model and the table that do not, and nothing compares those.

**Recommended fix:** decide it on ERT-620, before the adapter. The second option is the one that
matches the house pattern — `UploadLink` carries its digest because the link *is* the credential's
record, whereas a session's digest is what the adapter needs to store it, not what the portal needs
to read. Either way, record it as a decision rather than discovering it as a compile error.

### HAR-05 — `MigrationTest` proves the end state and never the path  [Medium]

**Where:** `test/data/db/MigrationTest.kt` — every test; `resources/db/migration/V4__hr_users.sql:57-73`

**What:** all thirteen migration tests run `withFreshDatabase { migrate(it.config) }`. The idempotence
test (`run twice - applies nothing the second time`) proves the *runner* is idempotent, not that data
survives. The drift test proves the *destination* matches `Tables.kt`. Nothing migrates a database
that already holds rows.

`V4` is the first migration where that matters:

```sql
alter table employees drop column created_by;
alter table employees add column created_by varchar(8) not null;
```

Four columns are dropped and re-added, one of them `not null` with no default. Against a populated
table that is either a hard failure — PostgreSQL will not add a `NOT NULL` column without a default —
or, for the three nullable ones, a silent discard of whatever `created_by`, `originals_sighted_by`,
`reviewed_by` and `updated_by` held.

**Impact:** none today, and the migration was correct for an empty database, which is all that has
ever existed. The finding is that **every acceptance criterion ERT-120 wrote is about a fresh
database**, so this class of defect ships green by construction — and the next migration to touch a
column will be written against a UAT deployment that does have rows.

**Reachability:** the first migration applied to a database with data. ERT-1220/1230 made that a real
place.

**Test coverage:** none. The portability sweep would not catch it either — `drop column` is valid in
both dialects.

**Recommended fix:** one test. Migrate to V3, insert a row into `employees` and `app_settings`,
migrate the rest, and assert the rows survive with their values. It fails against V4 today, which is
the point — the assertion then becomes "a migration that destroys data is a decision someone has to
make deliberately", and V4 gets either a documented exemption or a data-preserving rewrite.

### HAR-06 — Global mutable state in the composition root, shared across every test in the JVM  [Low]

**Where:** `src/di/DataModule.kt:115` and `:124`

```kotlin
internal val jwtWarnings = mutableListOf<String>()
internal val notifierWarnings = mutableListOf<String>()
```

**What:** two file-level lists, appended while Koin builds `JwtConfig` and `PortalBaseUrl`, drained
and cleared by `configureKoin()`. The KDoc says: *"Written once during graph construction and read
once at boot, both on the startup thread."*

That is true of the application and false of the test JVM. Every Koin container the suite builds
appends to the same two lists; `testKoinApplication()` resolves without draining them; and neither
list is synchronised. A green suite shows nothing, because nothing asserts on their contents across
containers.

**Impact:** negligible in production — one boot, one thread, drained immediately. In the suite it is
cross-test mutable state, which is the precise class of defect `RepositoryTestBase` spends ~15 ms per
test to eliminate. It becomes a real failure the day a test asserts *which* warnings a boot raised, or
the day JUnit is configured for parallel execution.

**Test coverage:** none, and none is possible without asserting on the lists, which nothing does.

**Recommended fix:** the warnings belong on the value they describe. `JwtConfig.fromEnvironment`
already returns a wrapper carrying `warnings` — hold that wrapper in the container and let
`configureKoin()` read it, rather than having the binding push into a global on the way past. It
removes the hand-off the KDoc has to explain.

## Checked and healthy — do not trade these away

Several tasks below could plausibly undo one of these, which is why they are written down rather than
left as an absence of findings.

- **The harness's two deliberate fidelity costs were both paid for correctly, and the numbers are
  now on record.** Measured 2026-09-18 on `main` at `4e1c674`: **689 tests, 13.75 s wall, 0 failures**,
  of which 150 database-touching tests account for **2.88 s** — ERT-240's brand-new migrated database
  per test costs roughly **19 ms**. The slowest classes are Ktor route tests (`ErrorMappingTest`
  2.26 s, `UserRoutesTest` 2.04 s), not the database. ERT-220's *"lower the cost
  factor in tests rather than replacing the algorithm"* **was** taken — every test uses
  `BcryptHasher(cost = 4)` except `TokenDigestTest:64`, which uses the production cost **because it is
  the test asserting the PIN gets a work factor**. That is the one place the default belongs. Do not
  "optimise" either of these.
- **One `suspend` transaction entry point with a correct `Dispatchers.IO` hop.** No blocking
  `transaction {}`, no `runBlocking` on a request path, and `Dispatchers` banned from the domain by a
  build-failing guard.
- **Invariants 3 and 10 are unrepresentable to violate, not conventions to remember.** `Denied`,
  `AuthenticationFailed` and `Forbidden` are field-less `data object`s mapping to shared `ApiError`
  constants; `Denied.code` is literally `"not_found"`, so an unmatched route renders the identical
  body. Any change to `AppErrorMapper` must keep this.
- **`AppError.toStatus()` is an exhaustive `when` over a sealed interface.** A new `AppError` case is
  a compile error at the mapper rather than a runtime 500, which is why it correctly has no test.
- **Every configuration reader but one uses `takeUnless(String::isBlank)`, and `APP_ENV` unset
  resolves to PRODUCTION**, so a typo lands on the strict side. SEC-31 is the single exception and
  the fix is to make it conform, not to relax the rule.
- **`HmacTokenDigest` builds a fresh `Mac` per call**, with the thread-safety reasoning recorded, and
  enforces its 32-character floor in dev as well as outside it — *"absence is forgiven in dev;
  weakness never is."*
- **`Slf4jUseCaseTracer` short-circuits on `!log.isDebugEnabled` before reading the clock**, so
  tracing is near-free when off.
- **The anti-vacuity discipline is real and it works.** `GuardOutcome`'s `Vacuous`/`Checked` split,
  `allTables.size shouldBe 14`, `IdTable` count 12, SQL file count 7, `handlers >= 8`,
  `receiving >= 5`. Several of the tasks below move one of those numbers; move it deliberately.

**Recorded 2026-09-18.** Nothing in this review was fixed during it; the two skills applied are
audit-only and the tickets are the output.

**Three findings gate work already in the queue**, and they are the ones to act on first: HAR-04

**Two candidates were investigated and dropped**, and they are listed under *Categories with no

**Three claims are explicitly not measured**, and are ranked accordingly: PERF-10 has no production

**The pattern behind most of these findings is one pattern.** Every HAR finding, and C29 to C33, is
a statement that was true when written and was not revisited when something beside it
changed — a fake that mirrored its adapter until the adapter learned an `ORDER BY`, a criterion that

build. It has six such guards and none pointed at the harness, which is why TASK-33 is a guard and a
contract suite rather than six patches.
